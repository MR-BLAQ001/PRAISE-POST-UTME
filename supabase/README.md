# Supabase production path

PRAISE POST UTME ships as a **demo-first** application. The complete product —
accounts, practice, timed CBTs, results, analytics, leaderboards, admin tools —
runs against a local browser store with no backend required.

This folder contains the production database path for operators who want hosted
accounts and multi-device data. The current UI does **not** switch over
automatically: `NEXT_PUBLIC_USE_SUPABASE` is a reserved flag, and an adapter
must be implemented and tested before you treat Supabase as the live data layer.
The demo store remains the source of truth in this repository.

## What is included

| File | Purpose |
| --- | --- |
| `schema.sql` | Tables, indexes, triggers, row-level security and the leaderboard function |
| `seed.sql` | Platform settings and setup instructions |
| `questions.seed.sql` / `questions.seed.json` | Generated by `npm run export:questions` |

## 1. Create a project

1. Create a project at [supabase.com](https://supabase.com).
2. Open **Project settings → API** and copy:
   - Project URL → `NEXT_PUBLIC_SUPABASE_URL`
   - Anon public key → `NEXT_PUBLIC_SUPABASE_ANON_KEY`
   - Service role key → `SUPABASE_SERVICE_ROLE_KEY` (server-only)
3. Copy `.env.example` to `.env.local` and fill those values in.
4. Never commit `.env.local` and never expose the service role key in a
   `NEXT_PUBLIC_*` variable.

## 2. Apply the schema

In the Supabase SQL editor:

1. Run `supabase/schema.sql`.
2. Run `supabase/seed.sql`.
3. Generate and load the question bank:

```bash
npm run export:questions
```

Then run the generated `supabase/questions.seed.sql` in the SQL editor. It
inserts all 800 seed questions with stable IDs and upserts on conflict.

If you use the Supabase CLI instead, copy these files into `supabase/migrations/`
and `supabase/seed.sql` according to your migration workflow. Keep the schema
idempotent: it is written with `if not exists`, `drop policy if exists` and
`create or replace` so it can be re-applied safely.

## 3. Create the first administrator

1. Register an account through Supabase Auth (email/password).
2. Promote it from the SQL editor:

```sql
select public.promote_admin('you@example.com');
```

`promote_admin` is executable by `service_role` only. It is deliberately not
available to signed-in clients.

The sign-up trigger `handle_new_user` creates a profile from the Auth metadata.
If you use the app's registration form with a custom adapter, pass:

```json
{
  "data": {
    "username": "ada_okafor",
    "display_name": "Ada Okafor",
    "school": "Federal Government College",
    "preferred_subjects": ["english-language", "mathematics", "biology"]
  }
}
```

## 4. Security model

- **Profiles** are readable only by the owner or an administrator. Email
  addresses stay in `auth.users` and are never copied into `profiles`.
- **Questions** are readable by any signed-in user; writes require an admin.
- **Results, practice, notes, bookmarks, plans and notifications** are scoped to
  the owner, with admin read access for moderation and support.
- **Leaderboard** data is exposed only through `public.get_leaderboard(...)`, a
  `security definer` function that returns display name, username, avatar and
  aggregate scores. It excludes guests, opted-out students, administrators and
  every practice mode. Email addresses and detailed answers are never returned.
- **Role escalation** is blocked by the `protect_profile_fields` trigger. A
  student cannot promote themselves or change their guest status.
- **Storage**: the `avatars` bucket is public-read; writes are restricted to the
  owner's `auth.uid()` folder.
- The service role key must only be used in trusted server code, scripts and
  admin tasks.

## 5. RLS verification checklist

Before going live, verify with a non-admin test account:

```sql
-- Should return only your own rows.
select * from public.results;
select * from public.notes;
select * from public.notifications;
```

- [ ] A student cannot select another student's results.
- [ ] A student cannot update another student's profile or role.
- [ ] A student cannot insert a question.
- [ ] A student cannot update platform settings.
- [ ] A student can call `get_leaderboard()` and receives only public fields.
- [ ] An administrator can read reports, manage questions and update settings.
- [ ] Deleting an Auth user cascades to that user's private data.
- [ ] The service role key exists only in server-side environment variables.

## 6. Wiring the adapter

If you implement Supabase in the UI, keep the existing domain types from
`src/lib/types.ts` and map tables as follows:

| App type | Table |
| --- | --- |
| `UserProfile` | `profiles` (+ `auth.users` for email/password) |
| `Question` | `questions` |
| `ExamResult` | `results` |
| `PracticeAttempt` | `practice_attempts` |
| `Bookmark` | `bookmarks` |
| `Note` | `notes` |
| `QuestionReport` | `question_reports` |
| `Notification` | `notifications` |
| `StudyPlanner` | `study_plans` + `study_tasks` |
| `DailyChallengeState` | `daily_challenges` |
| Achievement unlocks | `user_achievements` |
| `ActivityEvent` | `activity_events` |
| `DemoSettings` | `platform_settings` |

Keep server-side scoring: `/api/exam/submit` validates seed answers today, and a
production adapter should validate all submitted answers on the server before
writing a result. Custom/admin questions need a server-side answer store too —
do not trust a client-supplied score.

## Current limitation

This repository does not silently pretend Supabase is active. The admin settings
screen labels Supabase as **Prepared**, not **Enabled**, and the demo store
continues to power the app until an adapter is deliberately connected.
